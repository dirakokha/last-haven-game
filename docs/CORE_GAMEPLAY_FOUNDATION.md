# Core Gameplay Foundation — proposal after PR #3

**Scope of the first PR:** After the merge of PR #3, introduce shared character vitals and damage boundaries in the existing rooms. Keep the current movement controller, Walker AI, and weapon timings; extract a locomotion state machine only when there is a demonstrated gameplay need. Reuse the frozen side-view camera, art, audio and real controls. Keep story, eight-hour pacing, new levels, actual companions and shelter content out of this milestone.

## Boundaries and data flow

| Layer | Owns | Must not own |
| --- | --- | --- |
| Godot scene adapters | Input, `CharacterBody2D` velocity/collisions, swept world queries, scene mounting, spawn markers, authored interaction points, avatar presentation | Inventory rules, mission progression, save I/O, or unique combat logic per room |
| Gameplay components | Locomotion state, vitals, current weapon action, inventory/equipment, interactable transaction validation | UI widgets or animation deciding whether damage occurs |
| Immutable Godot `Resource` definitions | Item/weapon/ammo compatibility, stack/slot limits, attack or reload timings, room links and mission graphs | Mutable HP, magazine counts or quest progress. Runtime instances reference definition IDs. |
| Run session | One player state, world flags, container/world deltas, current room/checkpoint, objectives, state snapshots | Node references in saves, per-room copies of player state, or preference settings |
| Presentation | Persian HUD binds actual read models; animation, audio and effects subscribe to committed events | Mutating combat, item or save state just because a frame/widget appeared |

Input adapters build commands consumed in discrete physics updates. Separate **locomotion** (`grounded ↔ airborne`, dodge and disabled/dead) from **action** (`ready`, shoot recovery, reload phases, melee phases, weapon swap); a small explicit policy defines which pairs coexist. Preserve A/D facing, horizontal airborne shots, X locomotion/Y jumping, true obstruction, W for entrances and E for ordinary world interactions. Presentation reads the same melee impact marker physics consumes; it cannot emit gameplay damage. In the first milestone, existing contact checks forward an amount (and Walker knockback) to the target actor; only future callers with a real need should add a richer damage request. Typed signals communicate results locally; avoid a global bus carrying mutable game objects.

Definitions use readable immutable IDs such as `weapon.pistol.basic`, `ammo.9mm`, `room.court` and editor-authored unique placement IDs for containers, doors and pickups. Definitions are shared; mutable item instances store an instance ID, definition ID and only their necessary state. Validate duplicates and broken links at import/test time. Conditions depend on real state: an injury may bleed, bleed ticks reduce health, and using an appropriate dressing stops bleeding only if the use transaction succeeds. No cosmetic meters or empty interaction buttons.

## CharacterVitals contract

`CharacterVitals` is one `RefCounted` instance per actor, not an asset or service. Construction takes capacity (minimum 1) and starting HP (clamped to 0…capacity). `health`, `max_health`, and `is_depleted()` are read access; `apply_damage` and `apply_healing` return the actual HP lost/gained. Nonpositive amounts and changes to a depleted actor are ignored. `reset()` restores that instance's configured starting HP. `health_changed(previous, current)` runs after the state commits, followed by `depleted` only on the transition to zero. Observers cannot write recursively during notification. Construction is silent, and healing does not resurrect.

Contact checks stay in the projectile, bat and Walker attack. Runtime callers use the actor entry point so target policy/reactions run: the Player owns the 0.7-second immunity and damage cue, the Walker owns knockback, vocals and nonblocking corpse state, and the room listens for Player depletion to freeze simulation. HUD and art read vitals; neither approves a hit. A room transition carries only value snapshots into new actor instances; while indoors the absent Walker needs a snapshot, not a second actor or parallel HP field. Defeat restart makes a fresh scene, not a component-only revival: resetting HP alone intentionally does not reset an actor's collision, pose, or immunity.

## Firearm definition and runtime boundary (2A)

`WeaponDef` is an editor-authored `Resource`, shared and immutable by convention during play. It identifies the firearm and compatible ammo, supplies its display name, magazine capacity, reload/cooldown, damage, projectile speed/range and right-facing muzzle offset. Validation requires nonempty identifiers and name, positive counts/timings/range/speed, finite numeric offsets and positive forward X. The shipped pistol is `assets/weapons/pistol.tres`; its muzzle is measured from the existing actor pin. Construction with an invalid definition yields an inert `WeaponInstance` rather than live ammunition.

A `WeaponInstance` owns only its loaded magazine. It starts full, consumes one round on a successful firing request, accepts only matching reload rounds within capacity, and can restore a clamped magazine snapshot. The `SideWeapon` controller runs the existing shot/reload inputs, recoil and timing. It mirrors muzzle X only, checks shoulder-to-muzzle obstruction, and supplies `SideProjectile` with speed, range and damage per shot. Projectiles still sweep horizontally and apply hits through the Walker and `CharacterVitals`. Bat timing, collision and presentation stay in their existing code path.

Reserve stock is private to `SidePlayer`, keyed by ammo ID. On reload completion the controller requests up to the remaining capacity through `take_reserve` and loads only what was actually supplied; `reserve_for` reads availability. This small count/take boundary can be backed by a future inventory without replacing shot or reload logic. Reload cues retain the existing pistol moments by using the same fractions of duration for all definitions. The fixed pistol loadout carries the existing magazine and pistol reserve value snapshots across doors; there is no persistent save. Extend that snapshot only when multiple loadouts or stocks become playable. The alternate definition lives under `tests/fixtures` and is not an option in the game or in export.

## Shared side-view interaction (repository PR #6)

`SideInteractable` is an authored Marker2D with a unique, stable `placement_id` (not its node name/path), a translatable prompt, an InputMap action, horizontal reach, vertical tolerance and an enabled flag. It registers in the `side_interactables` group. `can_activate(actor)` checks the actor is active, alive and grounded, both distances are strictly inside the bounds, and the object is enabled, configured and available. `activate(actor)` rechecks all guards and returns whether the local transaction succeeded. Subclasses implement availability and activation; they do not poll input or update HUD widgets.

`SideRoom` considers only registered descendants of the active room. It selects the nearest usable object by horizontal distance; exact ties use lexicographically smaller placement ID, then node path only as a fallback for duplicate IDs. This keeps an unchanged scene's selection stable. Only the selected object's configured action is accepted; there is no fallback to another nearby object if the player presses the wrong key. The existing HUD uses the resolved key label with an LTR isolate inside the Persian prompt. Pause, defeat and transition block interaction. Portals still use W, their authored destination/arrival markers and existing reach; invalid destinations are not selectable. A successful door activation starts the existing fade and value transfer, which freezes the active actor until the new scene is ready.

The Warehouse box (`warehouse.pickup.9mm.01`) uses E and adds exactly **12 `ammo.9mm` rounds** to `SidePlayer` reserve, leaving the loaded magazine untouched. It has no collision or inventory item definition. A successful grant records its placement ID synchronously and immediately hides/disables the box before freeing it. Rebuilding the room suppresses placements that are already collected. `SideRunState` is a small `RefCounted` held by the SceneTree; it contains **only in-memory collected placement IDs**. It survives door scene changes and is cleared on an explicit defeat restart. It does not write files, own actor snapshots or constitute the future `RunSession`.

After importing in Godot 4.7.2 Standard, run `godot --headless --path . --script res://tests/side_interaction_test.gd` to exercise both interactions using their real keys.

The initial gameplay PR should not pre-build the entire state layer. Use stable IDs and interfaces where there are active callers, then promote the real state to the session in the persistence PR. The eight-hour campaign will assemble reusable rooms, loot tables, encounter and objective definitions after these vertical tests, not before.

## Persistence contract (for PR 4, not implemented here)

- Serialize an explicit versioned value snapshot under `user://`: slot metadata, checkpoint room/arrival, player vitals and injuries, inventory/equipment and magazines, durable placement deltas, objective/decision flags. Commit only at a stable boundary. Never serialize `NodePath` as an identity, scripts, animation timers, projectiles, fades or signals. F2 and other user preferences remain a separate file.
- Validate types, IDs, bounds and supported schema before mutating the active session; known old formats migrate in memory, future formats fail safely. Rebuild via the room registry and authored placement IDs. Resolve missing references with an explicit tested fallback or reject with localized feedback.
- Write a staged file, close and verify it, preserve the last known-good backup, promote the staged file in the same directory, then verify successful load. Do not assume overwrite rename is atomic on Windows: test the actual platform behavior and recover from leftover temp/backup after interruption. Failed load must not destroy the run or current slot.
- Test fresh save, backup recovery, intentional wrong version, and process restart with the official Windows build. Keep selected fixture saves checked in for schema migration tests; do not ship active development saves.

## HUD strategy

Keep the current functional Persian HUD. Add only controls necessary to operate each new system and expose truthful read models. After inventory, equipment, ammo, injuries and survival behavior exist, design the final interface around those actual conditions, with real usability tests for RTL, mixed-direction labels, keyboard navigation and native-scale legibility. No hunger, thirst or other decorative indicators by default.
