# Core Gameplay Foundation — proposal after PR #3

**Status: design only.** Start after the owner's Windows acceptance and merge of PR #3, in a new session from updated main. The first new PR should prove reusable movement and combat boundaries in the existing rooms, not start the campaign or finalize the HUD. Reuse the frozen side-view camera, art, audio and real controls. Keep story, eight-hour pacing, new levels, actual companions and shelter content out of this milestone.

## Boundaries and data flow

| Layer | Owns | Must not own |
| --- | --- | --- |
| Godot scene adapters | Input, `CharacterBody2D` velocity/collisions, swept world queries, scene mounting, spawn markers, authored interaction points, avatar presentation | Inventory rules, mission progression, save I/O, or unique combat logic per room |
| Gameplay components | Locomotion state, vitals, current weapon action, inventory/equipment, interactable transaction validation | UI widgets or animation deciding whether damage occurs |
| Immutable Godot `Resource` definitions | Item/weapon/ammo compatibility, stack/slot limits, attack or reload timings, room links and mission graphs | Mutable HP, magazine counts or quest progress. Runtime instances reference definition IDs. |
| Run session | One player state, world flags, container/world deltas, current room/checkpoint, objectives, state snapshots | Node references in saves, per-room copies of player state, or preference settings |
| Presentation | Persian HUD binds actual read models; animation, audio and effects subscribe to committed events | Mutating combat, item or save state just because a frame/widget appeared |

Input adapters build commands consumed in discrete physics updates. Separate **locomotion** (`grounded ↔ airborne`, dodge and disabled/dead) from **action** (`ready`, shoot recovery, reload phases, melee phases, weapon swap); a small explicit policy defines which pairs coexist. Preserve A/D facing, horizontal airborne shots, X locomotion/Y jumping, true obstruction and W as contextual interaction. Presentation reads the same melee impact marker physics consumes; it cannot emit gameplay damage. A damage request carries source, amount, type and contact; the world adapter validates collision and the target's vitals applies the rules once. Typed signals communicate results locally; avoid a global bus carrying mutable game objects.

Definitions use readable immutable IDs such as `weapon.pistol.basic`, `ammo.9mm`, `room.court` and editor-authored unique placement IDs for containers, doors and pickups. Definitions are shared; mutable item instances store an instance ID, definition ID and only their necessary state. Validate duplicates and broken links at import/test time. Conditions depend on real state: an injury may bleed, bleed ticks reduce health, and using an appropriate dressing stops bleeding only if the use transaction succeeds. No cosmetic meters or empty interaction buttons.

## Independent PR milestones

| PR | Deliver and demonstrate with the current rooms | Acceptance / regression |
| --- | --- | --- |
| **1 — Movement and combat boundaries** | Extract a reusable controller with keyboard adapter, locomotion/action states and an actual reusable vitals component. Port the existing pistol and bat without changing player-facing rules; keep damage, recovery, timing and in-air behavior. Use a small health test fixture, not another map. | Fixed-step input tests for walk/run, obstacle, one jump, dodge, pause/death, 2-direction muzzle sweep, preflight, melee marker and health clamping. Gate 2/3 art and gameplay regressions still pass. |
| **2 — Weapons and injury loop** | Define `WeaponDef` and per-instance magazine state; expose actual compatible ammo, equip/swap, reload and melee commands. Demonstrate a second weapon definition with meaningfully different handling using an existing test fixture, not a new environment. Add damage types, injury/bleeding state and real healing/use effects. | Invalid reload/swap doesn't consume ammo. Switch restores the correct loaded magazine; cancellation follows documented commit markers. Validate obstruction, melee single-hit, deterministic bleed ticks and dressing/health behavior. |
| **3 — Items, equipment, and loot** | `ItemDef`, bounded slots/stack limits, equipment compatibility, ammo item stocks, container contents and empty state. Environmental pickups and one loot container in an existing scene behind the common `Interactable` contract. Real take/equip/use actions with only the minimum usable Persian inventory controls. | Capacity overflow leaves the remainder in the world/container; no duplication on repeated interaction. Invalid use, full bag and empty-container cases return useful outcomes. Equip/consume/transfer operations conserve quantities and emit one result. |
| **4 — Room transition and persistence** | Reusable interaction selection and door guards, data-driven `RoomLink` with source/destination and arrival IDs. Consolidate side-room metadata into a `RunSession` and snapshot at safe checkpoints. Add versioned save/load, with a restart proving the same inventory, injury, looting and room flags. | Both travel directions, wrong/locked portal rejection, bad destination/spawn recovery, reload/transition guard, save round-trip after process exit, unsupported/corrupt save recovery, no losing the last good save when a write fails. |
| **5 — Objectives and progression hooks** | Run one real objective chain using validated gameplay events, e.g., collect a specific item, then unlock a route/return. Provide stable mission/objective IDs, prerequisites, progress and completion stored via the session. Only add branching flags/rewards when there is a working objective consumer. | Out-of-order/repeated events don't double grant rewards or bypass prerequisites. Checkpoint restores progress, completion and branch flags; transient scene unloads don't lose them. |
| **Later — Companion and shelter modules** | Companions own relationship/order/status state and use movement/interactions; shelter owns stash, upgrades, repair or crafting through real inventory transactions. Separate PRs with an end-to-end interaction each. | Validate save compatibility and resource consumption. Narrative choices, shelter upgrades, weapon variety and multiple campaign rooms use shared definitions and contracts, not scene-specific forks. |

The initial gameplay PR should not pre-build the entire state layer. Use stable IDs and interfaces where there are active callers, then promote the real state to the session in the persistence PR. The eight-hour campaign will assemble reusable rooms, loot tables, encounter and objective definitions after these vertical tests, not before.

## Persistence contract (for PR 4, not implemented here)

- Serialize an explicit versioned value snapshot under `user://`: slot metadata, checkpoint room/arrival, player vitals and injuries, inventory/equipment and magazines, durable placement deltas, objective/decision flags. Commit only at a stable boundary. Never serialize `NodePath` as an identity, scripts, animation timers, projectiles, fades or signals. F2 and other user preferences remain a separate file.
- Validate types, IDs, bounds and supported schema before mutating the active session; known old formats migrate in memory, future formats fail safely. Rebuild via the room registry and authored placement IDs. Resolve missing references with an explicit tested fallback or reject with localized feedback.
- Write a staged file, close and verify it, preserve the last known-good backup, promote the staged file in the same directory, then verify successful load. Do not assume overwrite rename is atomic on Windows: test the actual platform behavior and recover from leftover temp/backup after interruption. Failed load must not destroy the run or current slot.
- Test fresh save, backup recovery, intentional wrong version, and process restart with the official Windows build. Keep selected fixture saves checked in for schema migration tests; do not ship active development saves.

## HUD strategy

Keep the current functional Persian HUD. Add only controls necessary to operate each new system and expose truthful read models. After inventory, equipment, ammo, injuries and survival behavior exist, design the final interface around those actual conditions, with real usability tests for RTL, mixed-direction labels, keyboard navigation and native-scale legibility. No hunger, thirst or other decorative indicators by default.
